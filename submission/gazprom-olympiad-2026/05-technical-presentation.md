# Обновлённая техническая презентация

## Общий принцип

Техническая презентация должна служить приложением к защите и подтверждать инженерную состоятельность проекта. Её задача - не дублировать бизнесовую часть, а показать архитектуру, режимы связности, модель данных, сетевые последовательности и фактически реализованные механизмы.

## Что уже хорошо в текущей технической презентации
- Есть компонентная архитектурная диаграмма.
- Есть ER-диаграммы по inventory и коммуникационному контуру.
- Есть последовательности по пакетам, звонкам и файлам.
- Есть реальные экраны desktop-прототипа.

## Что нужно исправить
- Слишком длинные текстовые слайды лучше превратить в схемы и короткие тезисы.
- Терминологические слайды сократить до приложений или примечаний.
- Начало презентации перестроить под техническую логику: задача, ограничения, контуры, режимы.
- Добавить отдельные схемы:
  - online/offline режим;
  - peer sync и central sync;
  - сценарий комиссии;
  - верхнеуровневая модель данных и привязка обсуждений к объектам.

## Что именно показывать на ключевых технических слайдах

### Слайд 4. Компонентная архитектура
- Оставить существующую компонентную схему как основу.
- Добавить подписи:
  - «клиентские устройства»;
  - «локальный контур»;
  - «mesh-коммуникации»;
  - «central sync».
- Упростить текст на слайде до 4-5 коротких тезисов.

### Слайд 6. Online/offline
- Явно разделить:
  - доступные операции без интернета;
  - операции, которые отложены до синхронизации.
- Подчеркнуть, что offline касается не только просмотра, но и работы с объектами, коммуникациями и вложениями.

### Слайды 7-8. ER-модели
- Не пытаться читать на защите всю диаграмму целиком.
- Выделить цветом или рамкой только 5-7 сущностей верхнего уровня.
- Объяснять не таблицы, а связи:
  - объект -> сессия -> комментарий -> вложение;
  - conversation -> thread -> file transfer -> call session;
  - peer device -> sync state -> sync change.

### Слайды 10-12. Последовательности
- Сохранить существующие sequence-диаграммы.
- На правой стороне оставить короткий список шагов.
- Убрать многословные абзацы.
- В звонках явно отметить:
  - signaling идёт через mesh-контур;
  - media согласуется через SDP/ICE;
  - WebRTC backend подтверждён для Android и desktop-клиентов в текущем проекте.

### Слайд 14. Синхронизация
- Показать две разные синхронизации:
  - peer-level локальное взаимодействие;
  - central-level консолидация.
- Это важный тезис, который отличает проект от обычной централизованной системы.

### Слайд 17. Статус и тесты
- Указать только подтверждённые вещи:
  - API `MeshNode`;
  - inventory screens;
  - hybrid sync logic;
  - tests `CentralHybridServicesTest`, `InventoryCodeServiceTest`, `InventoryLabelServiceTest`, успешно выполненные 24.03.2026.

- Слайд 10: ER инвентаризации.
- Слайд 11: ER коммуникаций и синхронизации.
- Слайд 13: обработка входящего сетевого пакета.
- Слайды 14-19: звонки и передача файлов.

### Нужно сократить и отдать в приложение

### Нужно использовать как демонстрационный блок
- Слайды 24-54 с прототипом.

## Рекомендуемый порядок показа прототипов в технической части
- Desktop: главная, dashboard, список оборудования, фильтры, правка объекта.
- Inventory: печать/маркировка, scanner flow.
- Communication: pairing, чат, файлы, звонок.
- Profile/diagnostics: статус узла, endpoint, topology.

## Чего не писать в технической презентации
- Не писать, что проект полностью внедрён.
- Не писать, что все среды и платформы уже поддержаны.
- Не называть центральный контур завершённой промышленной системой, если показывается только клиентская интеграция.
- Не приписывать проекту функциональность, которая в материалах не подтверждается.

## Главный тезис технической защиты

Проект технически интересен не количеством экранов, а сочетанием трёх вещей:
- локально автономный предметный контур инвентаризации;
- встроенный распределённый коммуникационный стек;
- последующая синхронизация с центральным контуром.

Именно это сочетание следует сделать осью всей технической презентации.
